# 文档编写约定

这套文档的验收对象是第一次接触 Clumsies 的读者：**他应能沿阅读路线理解产品、设计、数据和接口，再根据需要找到实现依据。** 术语准确和内容完整，不等于要把内部实现一次性全部摆在读者面前。

## 内容如何组织

| 内容类型 | 回答什么问题 | 当前入口 |
| --- | --- | --- |
| 入门解释 | 它是什么，为什么这样设计？ | [概览](/zh/overview)、[架构](/zh/architecture) |
| 结构与原理 | 核心对象、字段、关系和不变量是什么？ | [数据结构](/zh/data-model)、[完整流程](/zh/flows) |
| 操作指南 | 我怎样完成一个任务，怎样确认成功？ | [使用指南](/zh/guides/) |
| 接口参考 | 输入、输出、权限、前置条件、错误和版本规则是什么？ | [领域接口](/zh/reference/domain-api)、[HTTP](/zh/reference/http-api)、[MCP](/zh/mcp) |
| 详细设计 | 一个子系统怎样实现这些行为？ | Server、Runtime、Memory、Review、检索专题 |
| 历史与证据 | 过去改变了什么？某次测量证明了什么？ | 历史页面、[性能专题](/zh/performance/) |

同一主题保留一个当前详细说明；入门页只解释必要概念并链接到它，不复制整份规范。中英文使用对应路由，主线的内容深度和事实保持一致。

## 每页应怎样写

1. 开头说明本页能帮助读者解决什么问题，以及必要的前置阅读。
2. 先用实际场景解释概念，再给对象名和字段名。贯穿示例使用虚构的“部署回滚清单”，不使用用户真实数据。
3. 数据结构写清身份、归属、关键字段、可空值、关系和版本边界；区分数据库行、HTTP 响应和本地派生对象。
4. 接口按领域和用例组织。示例标明完整请求还是字段节选，以及 ID、哈希、ETag 等占位值从哪里取得。
5. 跨进程流程写出持久化点、完成条件、失败结果和恢复方式。尤其区分本地保存、同步与发布。
6. 图用于说明关系；正文提供同等信息，图片提供替代文本和原图链接。图中的实体、箭头和状态必须经过实现核对。
7. 在末尾提供少量精确源码或测试入口，便于继续深入。历史路径可以保留，但正文开头必须标明历史属性。

## 怎样判断内容是否准确

代码、数据库 migration、HTTP 路由、Rust/Swift 类型和可执行测试共同构成实现依据。OpenAPI 的路由覆盖检查不能证明每个 schema 字段和运行行为都一致；已知差异在 [HTTP 契约](/zh/reference/http-api) 集中说明。

不要把设计目标写成当前保证，也不要把某次本机测试写成生产性能承诺。页面介绍当前实现；有时间范围的性能证据必须带范围和限制。本文档重组以代码基线 `5d038ff` 核对，源码证据链接可固定到该提交；修改相应实现时同时更新说明与链接。

## 提交前检查

- 从[文档首页](/zh/)沿主线走一遍：遇到的名词是否已解释？下一页是否回答自然产生的问题？
- 对照代码检查示例、状态转换、权限和错误；检查中英文是否表达同一事实。
- 执行站点构建，并检查导航、正文链接、图片和 JSON 示例：

```sh
bun install --frozen-lockfile
bun run build
bun dev/check-docs-search.mjs
```

- 涉及 HTTP 契约时，执行仓库已有的路由覆盖测试：

```sh
cargo test -p server --lib axum_routes_match_public_and_admin_openapi
```

- 检查桌面和窄屏阅读，表格应可横向滚动，架构图可打开原图。构建通过只证明产物可生成，不能替代内容审核或接口行为测试。
