# macOS 错误反馈审计与修复

审计日期：2026-09-21。基线：`940d5830`。实现分支：`codex/macos-error-feedback`。本报告描述工作区中的修复，不代表已经发布。

## 结论与范围

问题来自三层叠加：请求边界把技术错误当作界面文案；不同页面各自展示同一次失败；加载状态又没有区分首次失败、后台刷新失败和用户操作失败。只删掉红字会隐藏真实失败，只替换文案也无法消除重复提示。

检查覆盖 `apps/macos/Sources` 的全部 127 个 Swift 文件，包括 App 生命周期、网络与 XPC 边界，以及 Inbox、Memory、Reviews、Bundles、Dashboard、Activity、项目、组织管理、设置和诊断界面。搜索结果中的引用数量不等于缺陷数量；下表按实际问题归类。

## 已修复的问题

| 范围与代码入口 | 原有问题 | 修复后的行为 |
|---|---|---|
| `ServerClient`、`DaemonXPCClient`、`DaemonXPCError` | HTTP 状态、响应正文、请求 ID、解码路径进入页面 | 按错误类型生成本地化提示；诊断信息保留在原有日志通路 |
| `AuthenticationClient`、`NativeServerSetupClient`、启动流程 | 登录服务和本地服务错误携带技术原文 | 保留登录、重新打开应用等可执行指引，隐藏原始载荷 |
| `WorkspaceView`、`SettingsWindowView` | 多个局部区域反复报告失败；横条挤压侧栏布局 | 所有非阻断反馈统一为右下角文字提示；取消请求不提示；设置图标不参与反馈布局 |
| `WorkspaceCoordinator.reload` | 已有工作区刷新失败后隐藏主窗口，进入启动失败页 | 临时服务故障保留主窗口和内容；首次加载失败仍有恢复入口；旧账号请求不能更新新账号界面 |
| `InboxView` | 欢迎消息使用 sheet，已读失败在父页和弹窗重复出现 | 正文在主窗口内导航展示；消息页面移除列表筛选工具；点击阅读即更新已读 |
| `InboxStore` | 已读和归档依赖网络成功，离线时反复报错 | 先记录本机待同步操作并更新界面；沿用现有刷新周期补交；读状态与归档状态独立；永久失败回滚并提示 |
| `InboxStore.refresh` | 拉取失败显示“没有通知”；状态探测失败制造一条通知 | 首次失败显示可重试的不可用状态；刷新失败保留通知；探测失败保留已知同步状态，不制造业务通知 |
| Reviews、Draft reconciliation | 详情加载同时写入局部错误和全局错误；编辑 sheet 上再弹错误 alert | 单一反馈位置；提交失败保留表单与冲突处理结果，在当前任务中显示恢复信息 |
| Memory、Guidelines、文件操作 | 直接展示底层错误；后台更新触发“操作失败” | 统一分类；网络类后台错误不再占用操作失败条；保留保存失败、部分操作完成、版本冲突等必要提示 |
| Bundles、Drafts、Reviews 集合 | 刷新失败提示与连接状态重复 | 保留旧内容；连接状态已显示时不再重复刷新错误条；首次不可用与成功空结果保持区别 |
| Dashboard、Activity | 重复错误条；后台刷新失败干扰已有内容 | 保留已加载数据；首次加载、分页失败仍有明确的重试位置 |
| 项目仓库、存储和成员操作 | 刷新先清空仓库；存储迁移错误原文直出 | 同项目同账号刷新保留仓库；账号或项目变化清空旧数据；存储失败使用恢复文案 |
| 组织管理 | 父页和子页面重复报错；缓存状态使用警告样式 | 缓存、操作、分页反馈统一移到窗口右下角；保留缓存只读限制与重试入口 |
| 检索诊断 | 刷新失败清空历史和详情；首屏失败仍称“没有记录”；翻页错误出现在详情区域 | 保留已有记录；失败和空结果分开；分页失败在窗口右下角提供重试；新选中记录加载失败不会显示上一条详情 |
| 取消、导出、本地文件错误 | 只识别 `CancellationError`，遗漏 URL/Cocoa 取消；ZIP 退出码进入文案 | 常见取消统一静默；磁盘空间和访问权限给出对应指引；导出错误隐藏技术码 |

## 提示位置与语义复查

网络横条只是其中一处。复查还处理了 Inbox 回执错误、Memory / Bundles / Reviews 刷新条、工作区底部错误条、Activity 分页错误、组织管理缓存和操作提示、项目表单错误区、诊断导出和分页错误。

反馈分成两类，不能把所有错误放进同一种浮层：

- 窗口级连接／缓存状态：右下角的图标和文字，使用次要文字色；没有背景框、圆角、阴影或自动消失计时器，不占据侧栏和正文布局。`pageFeedback` / `feedbackHost` 仍保证每个窗口只展示一条非表单反馈，重复来源一起关闭。显式操作失败用错误色，连接状态保持低强调。
- 表单内保存／提交失败：项目创建和编辑、组织名称和域名、组织和项目成员、Review 提交、Draft reconciliation、登录设置，均在当前表单内显示红色错误文字加图标。保留输入和原生操作按钮，重试时清理旧错误；不再在表单上叠加卡片。只在明确识别字段错误时指向相应字段，未知 HTTP 400 不能当作某个字段有错。

ServerClient 的写请求失败仍抛给调用方，但不再同时生成窗口级服务提示；GET / HEAD 的读取和刷新失败维护连接状态，避免保存失败在弹窗内外重复出现。

设置侧栏图标跟随正文大小，占位与主窗口一样为 16 × 16 pt，在连接和认证失败时也不变。真正的首次加载失败、无权限或对象不可用状态仍属于内容本身；字段校验、删除确认、未保存编辑保护和历史诊断记录保留。

颜色不能是错误的唯一表达，因此红色同时配有错误文案和图标。[Apple：Differentiate Without Color Alone](https://developer.apple.com/help/app-store-connect/manage-app-accessibility/differentiate-without-color-alone-evaluation-criteria)

## 统一处理规则

| 场景 | 展示与恢复策略 |
|---|---|
| 后台刷新遇到断网、超时、500/503、本地服务不可用 | 保留内容，窗口级服务状态；不弹窗，不创建 Inbox 通知 |
| 首次加载失败、没有可用内容 | 在内容区域显示“无法加载”及重试入口，不能伪装成空列表 |
| 用户主动保存、提交、删除失败 | 明确说明操作没有完成，保留输入与当前任务；不自动重复有副作用的请求 |
| 400/422 | 保留本地输入校验；未知服务端拒绝使用简明提示，不直接显示响应正文 |
| 401 | 提示重新登录；不自动注销或抛弃正在编辑的内容 |
| 403 | 提示访问权限发生变化，并指引刷新检查 |
| 404/410 | 表达对象已不可用；不当成断网，不据此制造成功结果 |
| 409/412 | 提示查看最新版本，沿用已有 reconciliation 流程 |
| 429 | 提示稍后重试，不增加高频重试定时器 |
| 请求取消或过期响应 | 不展示错误，不允许旧请求覆盖新页面或新账号 |
| 可恢复的已读/归档请求失败 | 保存在账号、组织和服务器隔离的本机队列，恢复后同步；新版本消息仍未读 |

请求 ID、原始错误和解码细节不属于普通业务界面。Activity 中用户主动展开的技术详情、检索诊断记录及隐私过滤后的日志是诊断入口，仍可提供技术证据。删除确认、放弃未保存编辑等需要用户决策的提示保留。导出失败和重启失败改为右下角反馈，不再弹出模态错误框。

## 依据与取舍

Apple HIG 建议谨慎使用 alert，并以 Mail 的连接状态为例：连接不可用可以用非打断式状态表达，启动离线时也可以展示缓存内容。[Apple HIG — Alerts](https://developer.apple.com/design/human-interface-guidelines/alerts)

欢迎消息没有要求用户立即决定的任务，因此使用常规导航阅读。HIG 要求模态展示有明确收益，并指出它会打断原有上下文。[Apple HIG — Modality](https://developer.apple.com/design/human-interface-guidelines/modality)

NN/G 强调按影响程度选择反馈、提供恢复建议、保留输入，并将技术代码留给诊断用途。它也支持在真正需要修正输入时就近提示，因此本次没有把所有错误都一律隐藏。[NN/G — Error-Message Guidelines](https://www.nngroup.com/articles/error-message-guidelines/)

窗口级状态、待同步通知回执和页面状态的具体组合是本项目的实现选择，并非 Apple 指定的一套固定组件。实现沿用原生 NavigationStack、现有 toolbar、日志和 30 秒数据刷新周期，没有引入通知框架或通用写请求重试器。

实机验收发现并修复了布局与文案问题：网络状态提示改为窗口右下角的轻量文字提示，不占据侧边栏或正文的布局空间；设置窗口也只展示一份窗口级提示，侧边栏图标不参与提示布局。通过断网前后的实际控件坐标检查布局没有位移。通知回执收到 400 时，通用文案错误地要求检查输入，现改为通知操作的刷新重试指引。

这不等同于生产环境故障演练；真实 SSO 重新认证、长时间断网及服务端大范围故障未在生产账号上执行。所有修复均需随该分支合并、构建后才会出现在正式安装的应用中。

## 重复实机故障测试

在当前 worktree 启动 `just dev-macos`，进入 Inbox，等待通知加载。以下命令每次执行一个，默认 60 秒后自动恢复，也可按 Ctrl-C 提前恢复：

```sh
just dev-macos-fault offline
just dev-macos-fault 500
just dev-macos-fault 400
just dev-macos-fault 404
```

| 模式 | 操作和验收 |
|---|---|
| `offline` | 刷新后继续阅读欢迎消息、标记已读或归档；内容保留，本机状态立即变化；恢复后刷新并检查服务端回执 |
| `500` | 刷新；保留通知，只有一条服务状态。daemon 的缓存回退会按暂时无法连接呈现，不应显示 500 原文 |
| `400` / `404` | 先选中通知，再点击“标为未读”；显示对应恢复指引，失败操作回滚；后台刷新不能冒充这个操作验收 |

工具只接受当前 worktree 的 loopback Local Instance，复用实例身份校验及生命周期锁；暂时停止它的 Server，构造真实 HTTP 失败，退出时恢复原 Server 并核对健康状态。App、daemon 和数据库保持运行；没有添加产品内的调试入口。技术错误体包含专用标记，验收确认该标记和请求 ID 没有出现在普通界面。

欢迎消息创建逻辑通过独立 PostgreSQL 测试验证：新用户首次签发会话时生成一次，正文存在，再次登录不会重发，已读和归档仍保留。实机截图复用 Dev 用户原有欢迎消息，通过正常回执 API 恢复可见和未读状态，不伪造第二次首次登录。
